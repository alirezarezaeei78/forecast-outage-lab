# Reporting-age fallback: protocol fixed before execution

Saved 12 October 2026 before executing this follow-up. This is **exploratory reuse** of the July–September 2012 benchmark already examined on 11 October. Yesterday's failures motivated the policy; this is not fresh independent validation, a new forecasting algorithm or a production result.

Question: can a deterministic freshness gate preserve ordinary-model forecasts when reports are current and avoid those forecasts when recent demand is unavailable?

New contribution: reusable causal report-age calculation, validated prediction router, and reproducible mixed-delay replay with per-row decisions, baselines, checks and figures. No model retraining or additional tuning. Reuse the nine previously fitted models' archived predictions at commit 4f7902fa147b5f8c40553d14363e45254dc54cce. Verify the original prediction bytes with SHA256 0695d32b6d75231478cdb849c4305490af836fb989db3ea3ddb8817f13ab493b. Derive actual report availability from the separately verified public UCI data; preserve natural gaps.

For target hour t, the forecast origin is the end of t−1. Age a is the number of hours by which the most recent observed, available report is older than t−1. Hide the preceding k reports for k=0,1,3,6, including every affected feature as in the original experiment. Search only the preceding 24 hours; if none is available, age is unknown/infinite and the gate falls back. Earlier hidden reports recover at subsequent appropriate origins; no permanent deletion is simulated. Report arrival timestamps are assumed known and trustworthy.

Fixed policy: ordinary HGB if age=0 and its forecast is finite/nonnegative; otherwise calendar-only HGB. The zero-age requirement is an engineering availability rule, not a threshold selected through a new test sweep. The router never reads target values, forecast errors or future observations. It requires finite/nonnegative fallback predictions and rejects malformed inputs.

Evaluate the four homogeneous scenarios and five mixed-delay schedules. For each seed 101–105, draw one delay per calendar day in chronological order, across all 92 test days, with probabilities [0.7,0.1,0.1,0.1] for [0,1,3,6] hours. Each day's delay applies at every rolling origin in that day. This is a **synthetic daily reporting-delay schedule**, not an estimated operational failure distribution. Save all five seeds; never choose the best seed. Daily blocks create correlated outages. The nominal delayed-day fraction is 30%; report the actual fraction.

Compare always ordinary, always outage-aware, always calendar, seasonal fallback, and the new age gate on identical observed rows. Primary metrics: MAE in rentals/hour and actual fallback frequency. Also report RMSE, each seed, each month and homogeneous scenarios. Display equal-weight averages of the five mixed schedules; these replays are overlapping uses of the same 2,208 targets, not 11,040 independent observations. No confidence intervals, statistical-significance claim or runtime comparison.

Budget: zero new estimator fits, five deterministic schedules and fixed routing. Use pinned repository dependencies; save exact executed environment, commands, source/data/code hashes, complete replay predictions and console output. Correctness checks cover future/hidden-target invariance, natural missingness, unknown/stale ages, invalid shapes/numbers, route selection, deterministic schedules, unchanged source bytes, identical rows and repeat-run numerical parity. Existing causal-feature checks also run. No assertion may require a positive performance outcome.

Limits: one historical city/quarter, already exposed benchmark, fixed old estimators, simulated outages shorter than 24h, trusted reporting timestamps, one original training mask per fold. Calendar fallback sacrifices demand-history information while stale. Wider outages, corrupt clocks, other cities and prospective untouched data remain untested. All findings, including costs or negative results, will be retained.
